Existing functionality

Weight Tracking, CS 360, April 2026

This artifact I chose for software design is a Java Android app with three screens: login, weight history, and SMS notifications. A user can create an account, sign in, log a weight, set a goal, and get a text when the goal is reached. Room holds a users table and a weight-entries table. The app already ran end to end.

Contact Service, CS 320, June 2025

This artifact I chose for algorithms is an in-memory Java directory. Contact stores an id, first name, last name, phone, and address. ContactService adds a contact, finds it by id, updates each field by id, and deletes it by id. A HashMap already keyed lookups by contact id. JUnit tests covered construction, duplicate ids, and field updates.

Grazioso Salvare, CS 340, February 2026

This artifact I chose for databases is a Python CRUD module and a Dash notebook over the Austin Animal Center collection in MongoDB. Rescue buttons filter the table. A pie chart and a map sit on the filtered rows. Staff could already search, update, and delete animal documents.

Code analysis

ArtifactFinding
Weight TrackingPasswords stored as typed text. Login opened the history screen with no user id, so the list loaded every row. The goal lived in one SharedPreferences value for the device. Room ran on the main thread. Schema changes wiped the database. Dates were always today.
Contact ServiceId lookup was already fast. There was no second path for last name or phone, and no sorted listing. Phone was checked for length, not digits. Empty ids and names passed a null-or-too-long check.
Grazioso SalvareA database password sat in the module and the notebook. Reads pulled a full Python list. Counts and breed charts were computed after the documents were already in memory. Update could run on an empty filter. The map could render the whole collection.

Planned enhancements

The review mapped each finding to a change, and mapped those changes to the five course outcomes.

  • Outcome 1, an environment that helps different audiences decide, stays with Grazioso Salvare: rescue filters plus a database-side summary for trainers, analysts, and leadership.
  • Outcome 2, professional communication, is the review itself, the README files, and the narratives on the next three pages.
  • Outcome 3, algorithmic trade-offs, stays with Contact Service: keep the id HashMap, add last-name and phone indexes, sort a copy, and measure the difference.
  • Outcome 4, standard tools used for operational value, is Room and hashing on the app, Java collections and JUnit on the directory, and MongoDB indexes, aggregation, and Dash on the shelter dashboard.
  • Outcome 5, a security mindset, is hashing and account isolation on the app, and removing the password from Grazioso source so a missing secret fails startup instead of falling back to a default.

The implemented results are on the artifact pages. This page records the plan, not the finished code.
