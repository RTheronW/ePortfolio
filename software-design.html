Milestone Two · Software design and engineering

Weight Tracking Android app

Artifact One · CS 360 · originally April 2026 · enhanced September 2026

The artifact

This artifact I chose is the Weight Tracking app I built in CS 360 in April 2026. It is a Java Android app with three screens: login, weight history, and SMS notifications. A user can create an account, sign in, log weight, set a goal, and get a text when the goal is reached. Data is stored in Room with a users table and a weight-entries table.

The CS 360 version already ran end to end, but the design was weak. Passwords were stored in plain text. Login did not pass a user id, so the history list loaded every row. The goal was one SharedPreferences value for the whole device. Room ran on the main thread, and schema changes wiped the database. Dates were always set to today.

Why it is here

I chose this project because it was a complete Android client, not a partial assignment. It already used Activities, Room, RecyclerView, and permissions, so I could improve structure and security instead of starting over. The components that showcase software-development skill are the authentication path, the Room schema, the data-access layer, and the main-screen workflow. Those four pieces decide whether the app is a demo or something that can hold personal health data. The enhancement work concentrated there.

The enhancement follows the Module Two code review. Passwords are hashed with PBKDF2 and a per-account salt. Login looks up the user by name, checks the hash, and sends the user id to the main screen. Weight rows and the goal now belong to that user. WeightRepository runs Room calls on a background thread. The database is version 3 with a written migration instead of a destructive reset. Users can enter a date, weights at or below zero are rejected, and the main screen shows current weight, goal, and remaining difference. I also extracted WeightAdapter, turned backup off, added file headers and a README, and wrote unit tests for hashing and input checks.

Course outcomes

This work covers the three outcomes I assigned to Artifact One in Module One.

Outcome 2 is professional communication. The README and class headers explain the design to another programmer. The progress header on the main screen shows current weight, goal, and remaining difference without opening the database.

Outcome 4 is using standard tools to deliver a more usable app. I kept Android and Room, added a repository so database work runs off the UI thread, wrote a version-3 migration, and added a date field plus JUnit tests for hashing and input checks.

Outcome 5 is a security mindset. Passwords are hashed, login passes a user id, and each account only sees its own history and goal. Backup is turned off so a device backup does not copy the local credential store.

Outcomes 1 and 3 will be covered with the other two artifacts.

What I learned

The CS 360 app ran, but identity stopped at login. Once I followed one account from create-user to the history query, it was clear why every user saw the same list, nothing after login still knew who was signed in. Adding the user id to the Intent, storing it on each weight row, filtering the queries, and moving the goal onto the user record all came from that one gap.

The other decision was how to handle the database upgrade. Wiping the tables would have been faster, but it would also have deleted existing accounts. Instead, I kept the original password column, stored the salt and hash in that same field, and wrote a migration that adds the new columns rather than dropping the tables. That kept local data intact and was the better design for this project.
