Milestone Three · Algorithms and data structures

Contact Service

Artifact Two · CS 320 · originally June 2025 · enhanced September 2026

The artifact

The artifact I chose is the Contact Service I built in CS 320 in June 2025. It is an in-memory Java directory. Contact stores an id, first name, last name, phone, and address. ContactService adds a contact, finds it by id, updates each field by id, and deletes it by id. Validation lives on the contact object. JUnit tests cover construction, duplicate ids, and field updates.

The CS 320 version already used a HashMap keyed by contact id, so add, find, update, and delete by id were average constant time. That path worked, but the design was still limited. There was no second way to find people, no sorted listing, and no measured comparison of search strategies. Phone values were checked for length, not digits. Empty ids and names passed because the check was null or longer than ten, not blank.

Why it is here

I chose this project because the id lookup was already solved. Replacing the HashMap with a list would not have shown new algorithm work. The components that showcase skill in algorithms and data structures are the primary id map, the last-name and phone indexes, the sorted listing, and the benchmark that compares those strategies. Those four pieces decide whether the directory is only fast by id or usable when the caller has a name or a phone number.

The enhancement follows the Module Two code review. ContactService still keeps a HashMap keyed by id for O(1) average add, find, update, and delete. A last-name index and a phone index were added so name and phone search do not scan the whole directory. registerContact and removeContact update all three maps. modifyLastName and modifyPhone move a contact out of the old bucket before they write the new value. searchByLastNamePrefix walks last-name keys instead of every contact. listAllSortedByName copies the values and sorts by last name, then first name. Validation now rejects blank ids, names, and addresses, and requires a ten-digit phone. New JUnit tests cover those cases plus index maintenance after a delete or a name change. A benchmark of 8,000 generated contacts showed last-name index lookup about 187 times faster than a linear scan. Id lookup stayed the fastest path. The extra memory for the two indexes is O(n).

Course outcomes

This work covers the two outcomes I assigned to Artifact Two in Module One.

Outcome 3 is design and evaluate a computing solution using algorithmic principles and manage the trade-offs. I kept HashMap for O(1) id lookup, added secondary indexes for name and phone, sorted a copy of the directory in O(n log n), and recorded a benchmark that compares linear scan, HashMap lookup, and the indexes, including the extra memory the indexes cost.

Outcome 4 is using standard tools to deliver that solution. I used Java collections for the three maps and JUnit 5 tests that prove prefix search, index maintenance after delete, and the stricter validation.

Outcomes 1 and 5 will be covered with the other two artifacts.

What I learned

The CS 320 service found contacts by id, but nothing else used a planned access path. Once I followed one contact from add to delete to a last-name change, it was clear the new index would go stale unless every write updated it. Removing the contact from the old last-name bucket before writing the new name, and doing the same for phone, all came from that one gap.

The other decision was whether to replace the HashMap or keep it and add indexes beside it. Replacing it would have made id lookup worse. I kept the original map for exact id operations and paid O(n) extra memory for the name and phone indexes. The benchmark made that trade-off visible: on 8,000 contacts the last-name index was significantly faster than scanning, and id lookup stayed the fastest call.
